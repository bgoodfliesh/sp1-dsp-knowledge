# SP-1 Audio System

## Audio Sample Rate and Format

**VERIFIED**

```
Sample rate:  48 kHz
Channels:     2 (stereo, L/R)
Bit depth:    typically 16-bit or 24-bit (depends on path)
Block size:   256 frames per I2S interrupt (≈ 5.3 ms @ 48 kHz)
```

## I2S Interface

**VERIFIED** (see hardware.md for pin details)

```
CS42L42:   I2S master (clock authority)
nRF52840:  I2S slave (audio source/sink)
TAS2505:   I2S slave (receives audio from nRF52840)
```

Clock source:
```
3.072 MHz external oscillator → CS42L42 → generates LRCLK + SCLK
```

I2S pins:
```
DOUT (data):   P1.09
LRCLK (frame): P0.11
SCLK (bit):    P0.12
```

48 kHz frame timing generated by the codec is authoritative. Do not redesign clock topology without hardware evidence.

## Audio Storage Format: Tape Stems

**VERIFIED** (from tape-looper firmware codebase)

### Overview

```
Bit depth:  24-bit
Sample rate: 48 kHz
Channels:   8 (4 stereo stems)
    Stem 0: Track 1 (L/R)
    Stem 1: Track 2 (L/R)
    Stem 2: Track 3 (L/R)
    Stem 3: Track 4 (L/R)
```

### Sector Structure

```
Physical sector size: 8192 bytes
Audio frames per sector: ≈ 340
```

Sector layout:
```
Offset      Size    Contents
0–2039      2040    Audio data
2040–2041   2       Timing/synchronization
2042–2043   2       Tempo
2044–2047   4       LED information
```

### Frame Layout

One audio frame = 24 bytes

Contains four stereo stem frames (one per stem):
```
Stem 0 (track 1):  bytes 0–5
Stem 1 (track 2):  bytes 6–11
Stem 2 (track 3):  bytes 12–17
Stem 3 (track 4):  bytes 18–23
```

Each 6-byte stem frame encodes stereo L/R samples.

### Unconventional Byte Reconstruction

**CRITICAL**: The stem frame uses an unconventional byte layout.

**Do not "fix" this to standard PCM without evidence.**

Given a 6-byte stem frame `data[0..5]`:

```c
int32_t left =
    (data[1] << 24) |
    (data[0] << 16) |
    (data[3] << 8);

int32_t right =
    (data[2] << 24) |
    (data[5] << 16) |
    (data[4] << 8);
```

Result: 32-bit signed integers (Q24 or Q16 depending on application).

This byte ordering is part of the known SP-1 audio storage contract. It must be preserved exactly when reading or writing tape files.

### Audio Block Interleaving

Audio frames are read in a specific order:

```
Frame indices: 0, 4, 8, 12, ...    (block 0)
               2, 6, 10, 14, ...   (block 2)
               1, 5, 9, 13, ...    (block 1)
               3, 7, 11, 15, ...   (block 3)

Block order: 0, 2, 1, 3
```

This interleaving pattern must be preserved for compatibility with saved sessions.

### Numerical Representation

**VERIFIED** (from tape-looper DSP constraints)

Audio samples and processing use **Q16 fixed-point arithmetic** throughout the audio path.

From `sp1-dsp-engineering/numeric.md`:
- Q16 = 16 integer bits + 16 fractional bits (signed 32-bit)
- Range: −32,768.0 to +32,767.999...
- Typical audio uses ±1.0 mapped to ±65536
- Saturation with `__SSAT()` prevents wraparound

When converting from storage (typically 24-bit) to Q16:
```
24-bit sample → left-shift to Q16 equivalent
```

Do not introduce floating-point arithmetic on the audio path. This is a non-negotiable constraint (see `sp1-dsp-engineering/SKILL.md` "Critical Audio-Path Constraint").

## Streamer Architecture

**VERIFIED** (from tape-looper firmware)

### Ownership and Responsibilities

eMMC is owned by a dedicated **streamer thread**.

Conceptually:
```
eMMC (4 GB storage)
  ↓
Streamer thread (sole eMMC owner)
  ↓
Ring buffer (pre-allocated, in-RAM)
  ↓
Audio thread (reads from ring, processes audio)
```

Audio thread **never** directly accesses eMMC.

### Ring Buffer Contract

**VERIFIED** (from REFACTOR_PLAN.md, Phase 3a)

```
Ring sample sizes: RING_SAMPLES = RRING_SAMPLES = 8192
```

Producer-consumer rules documented in `storage/ring_contract.h`:
- Streamer: producer (fills ring from eMMC)
- Audio: consumer (reads ring samples)
- Atomicity: alignment, ordering, and synchronization guarantees

Streamer thread handles:
- Sector reads
- Frame unpacking
- Ring write
- Storage-level errors

Audio thread handles:
- Ring reads (via safe API)
- Sample processing
- Effect application
- Output mixing

**Do not** allow audio thread to bypass the ring abstraction or directly access eMMC.

### Buffering Requirements

Buffer must account for:
- eMMC latency (varies, UNMEASURED on hardware)
- Audio consumption rate (deterministic: 48,000 samples/sec)
- Sector size (8192 bytes physical)
- Scheduling jitter

Exact buffer sizes should be established through measurement, not arbitrary convention.

### Underrun and Recovery

Audio underruns (ring buffer emptied before streamer refills) cause clicks/glitches.

Recovery strategies:
- Silence generation (mute until refilled)
- Rate adjustment (slow playback temporarily)
- Recording pause (if recording to empty buffer)

Do not leave underrun unhandled; it is an audible failure.

## Codec Initialization and Control

### CS42L42 Headphone Codec

**VERIFIED** (I2C address 0x48, pins P1.11/P1.07)

Initialization sequence must match established SP-1 firmware. Do not invent register sequences.

Codec provides:
- Headphone audio output (stereo)
- I2S interface to nRF52840
- Clock generation (master mode)

Reset sequence (from hardware.md):
1. Assert reset: P0.15 = 0 (active-low)
2. Wait (UNMEASURED, typically 10–100 ms)
3. Release reset: P0.15 = 1
4. Wait for codec ready
5. Initialize registers via I2C (0x48)

**Do not** redesign codec initialization without understanding register effects.

### TAS2505 Speaker Amplifier

**VERIFIED** (I2C address 0x18)

Amplifier receives I2S audio from nRF52840.

Reset sequence:
1. Assert reset: P0.09 = 0 (active-low)
2. Wait (UNMEASURED)
3. Release reset: P0.09 = 1
4. Wait for amplifier ready
5. Initialize registers via I2C (0x18)

SP-1-specific configuration (gain, EQ, protection) should remain explicitly documented. Generic TAS25xx initialization is insufficient.

## Real-Time Audio Path Constraints

**CRITICAL**: Audio callback execution is hard real-time.

### What the Audio Thread Must Do

Per 256-frame I2S interrupt (≈5.3 ms):
- Read ring buffer (pre-fetched audio samples)
- Apply effects (reverb, filters, mixing)
- Manage playback/recording state
- Update tape speed, position, effects parameters
- Produce I2S output

### What the Audio Thread Must NOT Do

- Block on I2C, SPI, or eMMC operations
- Allocate memory dynamically
- Call expensive functions (exp, sqrt) without precomputation
- Wait for external events
- Call Zephyr message queues in the callback
- Perform filesystem operations
- Access Bluetooth state without synchronization
- Use unbounded loops

Violating these causes:
- Audio glitches (clicks, pops)
- Buffer underruns
- Timing violations
- Loss of sync between audio/UI/storage

### Measurement and Budgeting

**UNMEASURED** on real hardware.

Audio thread has a budget of ≈5.3 ms per interrupt.

CPU, memory access, and cache behavior depend on:
- Total firmware load
- Other thread priorities
- Interrupt nesting
- Specific hardware state

Measure actual worst-case execution time on the real device before committing to effect complexity.

## Cross-Reference to DSP Engineering

The audio system boundary interfaces with the DSP layer through:

1. **Sample format**: 48 kHz stereo, Q16 fixed-point
2. **Block size**: 256 frames
3. **Real-time constraints**: No blocking, deterministic execution
4. **Numerical constraints**: Q16 only, no float on audio path
5. **Storage format**: Unconventional byte layout (must be preserved)

See `sp1-dsp-engineering/` for DSP implementation guidance:
- `audio-model.md`: hardware assumptions, per-algorithm requirements
- `realtime.md`: real-time safety rules, audit checklist
- `numeric.md`: Q16 fixed-point, saturation, rounding
- `validation.md`: testing and benchmarking audio DSP

The firmware provides the stable audio boundary. DSP operates within that boundary.

## Audio Path Initialization Checklist

When bringing up new audio functionality:

- [ ] Oscillator enabled (P0.13)
- [ ] CS42L42 reset released (P0.15)
- [ ] CS42L42 initialized via I2C (0x48)
- [ ] TAS2505 reset released (P0.09)
- [ ] TAS2505 initialized via I2C (0x18)
- [ ] I2S peripheral configured (DOUT, LRCLK, SCLK)
- [ ] Audio interrupt priority set appropriately
- [ ] Ring buffer allocated and initialized
- [ ] Streamer thread ready
- [ ] Audio callback prepared
- [ ] First audio block queued
- [ ] Audio verified on headphones (no clicks, correct pitch, stereo separation)
